응답하라 라디오 — 기획 통합 검토 및 수정 기준 v1.1
검토일: 2026년 11월 14일

1) 검토 범위와 판정
	1-1) 검토 대상
		대화에서 작성한 공식 양식 1~6번 초안, 사용자가 첨부한 contest-application-consent.docx, 공모전 및 Pleos 공식 문서를 대조했다. 첨부 Word는 미작성 접수양식이며, 이 작업에서 원본을 수정하지 않았다.
	1-2) 종합 판정
		세대 공감이라는 목적, 상황인지 AI DJ라는 구현 수단, 레트로 라디오라는 표현 방식은 유지한다. 다만 기능 범위, TTS 가정, 음원 공급, 사업 수치의 불일치를 수정해야 한다.
	1-3) 검토 한계
		문서 검토 결과다. 코드 실행, 에뮬레이터 시연, 음성 청취 평가, 사용자 조사, 음원 이용허락 확인은 수행하지 않았다. 아래 수정안은 구현 완료나 플랫폼 심사 통과를 의미하지 않는다.

2) 사용자와 확정한 사항
	2-1) 프로젝트명: 응답하라 라디오.
	2-2) 참가 형태: 2인 팀. 실제 개발 담당은 1인이다.
	2-3) 개발 담당: 전체 아키텍처, 풀스택 개발, 기술 총괄.
	2-4) 기획 담당: 서비스 기획, 발표, 일반 사용자 관점의 피드백과 사용성 검증.
	2-5) 핵심 가치: 서로 다른 세대가 음악을 매개로 추억과 취향을 공유하는 차량 내 공동 청취 경험.
	2-6) 팀명, 참가 부문, 대표자 지정, 연락처, 서명은 아직 확인되지 않았다.

3) 주요 검토 사항 및 수정 기준
	3-1) 경쟁 서비스 비교 — 제출 전 수정
		기존 초안: 기존 음악 서비스는 개인 취향에 집중하고, 공동 경험은 제한적이라고 일반화했다.
		확인: Spotify는 개인화 음악과 해설을 제공하는 DJ, 여러 사람의 취향을 결합하는 Blend를 제공한다.[S02][S03]
		수정: AI DJ나 공동 추천 자체를 독창성으로 주장하지 않는다. 두 시대의 음악을 연결하는 짧은 이야기, 차량 환경에 맞는 재생 제어, 레트로 방송 연출의 결합을 차별화 가설로 제시한다. 경쟁 서비스에 같은 조합이 전혀 없다고 단정하지 않는다.
	3-2) MVP와 시나리오 불일치 — 제출 전 수정
		기존 초안: 4번 시나리오는 ‘우리의 카세트’ 저장을 포함하지만 5번 개발 계획은 이를 제외했다.
		수정: 카세트 저장은 3번의 향후 기능과 6번 발전 계획에만 남긴다. MVP 시나리오에서는 세대 연결 방송과 청취 경험까지 설명한다. 음성 사연, 커스텀 음성 학습, 다수 DJ 캐릭터도 후속으로 통일한다.
	3-3) 미디어 서비스 누락 — 개발 착수 전 필수 검증
		확인: Pleos Music/Audio 가이드는 MBS 기반 차량 연동과 미디어 세션 제어를 요구한다. Android Media3의 MediaLibraryService는 MediaBrowserService 인터페이스에 대한 호환 경로를 제공한다.[S04][S05]
		수정: ‘Media3 + MediaSession’ 나열을 ‘MediaLibraryService + MediaLibrarySession + 콘텐츠 탐색 트리 + 차량 재생 제어’로 구체화한다. 최종 Pleos 호환성은 에뮬레이터와 대상 환경에서 확인한다. 레트로 자체 UI가 시스템 미디어 화면에도 그대로 나타난다고 약속하지 않는다.
	3-4) TTS 출력과 음성 파일 캐시는 별개 — 제출 전 수정 및 기술 검증
		확인: Pleos TTS 문서는 speak()/stop() 방식의 합성·재생, 완료·중단·오류 콜백, HYBRID/SERVER/ON_DEVICE 모드를 안내한다.[S06][S07]
		미확인: 조사한 공개 문서에서 합성 음성 파일의 앱 측 반환·저장, 임의의 감정 제어, 사용자 음성 학습 지원은 확인하지 못했다. 미확인을 미지원으로 단정하지 않는다.
		수정: 기본 캐시는 대본 텍스트와 편성 결과로 한정한다. 오디오 파일 캐시는 해당 공급자의 기술 지원 및 이용 조건이 확인된 경우에만 추가한다. 캐시 적중률 50% 가정은 비용 예측에서 삭제한다. 고유 DJ의 음색·억양 품질은 조기 청취 평가 대상으로 둔다.
	3-5) 정차와 주차를 혼동하지 않기 — 제출 전 수정
		확인: Pleos는 플랫폼의 CarUxRestrictions와 ActiveRestrictions에 따라 제한 기능을 제어하도록 안내한다.[S08]
		수정: ‘정차하면 상세 설정 허용’을 ‘플랫폼이 허용하는 상태에서 상세 설정 허용’으로 고친다. 신호 대기 중 속도 0을 제한 해제 조건으로 사용하지 않는다. 제한 상태를 읽지 못하면 상세 설정을 잠근다.
	3-6) 앱 실행과 오디오 포커스 복귀를 자동재생 명령으로 해석하지 않기
		확인: Pleos 가이드는 명시적인 사용자 행동 또는 시스템 재개 요청에 따른 재생을 요구하며, 오디오 포커스 손실 처리를 요구한다.[S04][S09]
		수정: 앱 실행은 설정 복원까지만 수행한다. 사용자의 재생 선택 또는 적법한 시스템 재개 요청 후 청취를 시작한다. 포커스 복귀 시에도 사용자가 직접 일시정지했는지 확인한다. 음악과 DJ 음성을 동시에 중단·복구할 수 있도록 하나의 조정자가 제어한다.
	3-7) 주행정보와 날씨를 과도하게 추론하지 않기
		확인: Vehicle SDK는 capability 확인 및 승인된 권한 범위의 사용을 요구한다.[S10]
		수정: 속도가 낮다는 이유로 교통 정체를 선언하지 않는다. 저녁이라는 이유로 퇴근길이라 부르지 않는다. 실제 날씨, 조회 시각, 제공 지역을 확인하며 데이터가 없거나 오래되면 날씨 멘트를 생략한다. 가족 관계, 성별, 나이도 선택된 음악 시대에서 추론하지 않는다.
	3-8) 음원 공급 및 권리 — 시연·상용화의 선행 조건
		현재 초안에는 실제 공급원, 이용허락 증빙, 곡 목록이 없다. ‘권리 확보된 음원으로 개발한다’는 계획이지 ‘이미 확보했다’는 사실이 아니다.
		수정: 곡마다 출처, 권리자, 허용 범위, 표기 조건, 시연·영상 공개·앱 포함 배포·오프라인 저장·저장소 공개 가능 여부를 기록한다. 확정 전에는 가상의 제목이나 미확보 음원을 재생 가능한 목록으로 설명하지 않는다.
		테스트 음원으로 재생 기술은 검증할 수 있지만, 그 결과가 실제 추억의 음악에 의한 향수·공감 효과를 입증하지는 않는다. 사용자 가치 검증용 콘텐츠는 별도로 검토한다.
	3-9) 장애 대응 보장 범위 — 제출 전 수정
		수정: AI 장애와 음원 공급 장애를 분리한다. AI가 실패해도 재생 가능한 곡은 계속 재생한다. TTS가 실패하면 기본 음성 또는 멘트 생략으로 전환한다. 네트워크가 없고 재생 가능한 로컬 음원도 없으면 재생 불가 상태를 안내한다. 모든 환경의 무중단 재생을 약속하지 않는다.
	3-10) MAU 및 리텐션 — 제출 전 수정
		기존 6개월 MAU 600명, 12개월 MAU 2,000명은 설치 규모의 근거가 없고 ‘누적 설치 × 40%’만으로는 검증된 예측이 아니다.
		수정: 해당 숫자를 예상 실적에서 제거한다. 지원 차량, 노출, 설치 전환, 활성 코호트가 확보된 뒤 월 신규 활성·기존 유지·복귀 설치를 중복 없이 합산한다. 계정 없는 차량 MVP는 사람 수 대신 익명 설치 단위의 월간 활성 규모를 대리지표로 측정한다고 명시한다.
		월간 활성 기준 제안: 해당 월에 60초 이상 재생한 고유 설치 ID 수. 실제 인원 수나 탑승자 수로 표현하지 않는다.
		4주차 재사용률 기준 제안: 최초 활성일부터 22~28일 구간에 다시 활성화된 설치 비율. 관찰 기간이 완료된 코호트만 분모로 사용한다. 기존 D30 20%는 실적·업계 기준이 아니며 삭제한다.
	3-11) 비용 모델과 방송 빈도 — 제출 전 수정
		기존 시나리오는 지속적인 방송 진행을 설명하지만 비용표는 세션당 멘트 2개, LLM 1회, 음성 캐시 50%를 가정했다. 세션 길이도 정의되지 않았다.
		수정: 고정 금액 예측 대신 청취 시간, 대본 호출량, 합성 문자·음성량, 공급자 단가, 서버·음원 비용을 분리한다. 캐시율은 실측 전 0%로 보수적으로 둔다. Pleos TTS의 요금 및 이용 조건을 확인하기 전 무료로 가정하지 않는다.
	3-12) 핵심 검증 시점 — 일정 수정
		기존 계획은 TTS와 차량 SDK 검증을 후반부에 배치했다.
		수정: 첫 개발 단계에서 에뮬레이터 설치, 미디어 탐색·재생, TTS 호출·중단, 플랫폼 제한 상태, 음원 확보 가능성을 검증한다. 이후 UI·대본·날씨·추천을 통합한다. 검증이 실패하면 미확인 기능을 축소하고 시연에서 구현 범위를 명시한다.

4) 수정된 개발 기준안 — 제안
	4-1) 범위
		MVP: 두 개의 선호 시대 선택, 균형 편성, 공통 주제 기반 연결 멘트, DJ 1개 캐릭터, 시간대·유효한 날씨 반영, 기본 레트로 UI, 미디어 제어·주행 제한·장애 대응.
		조건부: 승인된 위치·차량 데이터 활용. 데이터가 없을 때도 선호 시대·사용자 선택·시간대만으로 방송 구성.
		후속: 카세트 저장, 커스텀 음성 학습, 음성 사연, 여행지 추천, 다수 DJ, 학습 기반 개인화.
	4-2) 선곡 및 생성 책임
		앱의 편성기가 사용 권한과 재생 가능성이 확인된 후보에서 곡을 정한다. 세대 균형과 사용자 선택을 날씨보다 우선한다. LLM은 선정된 곡과 검증된 메타데이터에 대한 짧은 멘트만 생성한다. LLM에 재생 명령 권한이나 임의 URL 선택 권한을 주지 않는다.
	4-3) 방송 정책 초안
		사용자가 재생을 요청하면 준비된 음원으로 시작하고, 생성 지연 때문에 재생을 무기한 막지 않는다.
		일반 청취는 곡 사이 멘트만 허용한다. 첫 30분 기준 오프닝 포함 최대 3회, 회당 10~15초를 평가용 상한으로 제안한다. 후속 30분 구간도 최대 3회로 제한하며 사용자가 멘트를 끌 수 있게 한다. 이 수치는 사용자 테스트 전 제안값이다.
		공모전 짧은 시연은 멘트가 있는 구간을 발췌하고 ‘축약 시연’이라고 표시한다. 일반 방송 빈도를 시연 때문에 과도하게 높이지 않는다.
		다음 대본은 미리 준비하되 유효시간·현재 곡·세션 버전을 확인한다. 사용자가 곡을 넘기거나 세션을 종료하면 이전 대본과 지연된 응답을 폐기한다.
	4-4) 최소 아키텍처
		Android 앱: 미디어 서비스, 편성기, 재생 상태 조정자, 설정 저장소, 날씨·차량 데이터 어댑터, TTS 공급자 어댑터.
		백엔드: 단일 서비스에서 LLM 중계, 입력·출력 검증, 제한된 대본 캐시, 인증, 요청량 제한을 처리한다. MVP에서 마이크로서비스·별도 추천 학습 서버를 만들지 않는다.
		정책 설정: 멘트 길이·빈도, 요청 타임아웃, 유효시간, 기본 멘트 버전은 radio_policy.json 같은 설정파일로 관리한다. API 비밀키는 저장소나 앱에 넣지 않고 서버의 비밀정보 저장소로 분리한다.
	4-5) 보안과 운영
		서버에 API 키만 숨기는 것으로 끝내지 않는다. 요청 인증, 이용량 상한, 동시 요청 제한, 공급자 타임아웃, 장애 대체 경로를 둔다. 앱에 공통 비밀키를 내장하는 것을 사용자 인증으로 취급하지 않는다.
		LLM에는 날씨 요약·선호 시대·곡 메타데이터만 전송하는 것을 기본으로 하고 정확한 좌표·실명·가족 대화는 제외한다. 가족 대화를 녹음하거나 자동 분석하는 기능은 MVP에 넣지 않는다.
		공유 캐시에 개인 식별 정보가 담긴 대본을 넣지 않는다. 로그에는 키·정확한 위치·원문 개인정보가 남지 않도록 설계한다. 계측 데이터의 수집 목적·보관·삭제 기준을 정의한다.

5) 공식 양식 1~6번 통합 수정 초안
	5-1) 앱 한 줄 소개
		응답하라 라디오는 서로 다른 세대의 음악 취향을 날씨·시간대에 어울리는 레트로 AI DJ 방송으로 연결하는 차량용 세대 공감 라디오 앱입니다.
	5-2) 기획 배경
		본 프로젝트는 가족 등 서로 다른 세대가 함께 탑승한 차량에서 각자의 음악을 자연스럽게 소개하고 함께 즐길 수 있는 경험에 주목한다. 이미 개인화 DJ와 공동 취향 추천 서비스가 존재하므로, 단순한 추천 기능이 아니라 두 시대의 음악을 하나의 이야기로 연결하는 차량 내 방송 경험을 검증하고자 한다.[S02][S03]
		사용자가 각자의 선호 시대를 선택하면, 독자적인 레트로 DJ 캐릭터가 두 시대의 공통된 분위기를 짧게 소개하며 방송을 이어간다. 세대 간 대화 및 음악 발견 효과는 현재 기획 가설이며 사용자 평가로 확인할 계획이다.
	5-3) 앱 주요 기능 및 차량 특화 요소
		첫째, 두 선호 시대의 음악을 균형 있게 배치하고 공통된 분위기로 연결한다. 출생 연도나 가족 관계를 자동 추론하지 않는다.
		둘째, 시간대와 유효한 날씨 정보를 반영해 DJ 대본을 생성한다. 지원·권한이 확인된 차량 정보는 선택적으로 활용하며, 정보가 없으면 해당 표현을 제외한다.
		셋째, 레트로 DJ 1개 캐릭터의 대본과 짧은 시그널, 곡 사이 진행으로 라디오 감성을 구현한다. 음성 합성 품질과 출력 제어는 개발 초기에 검증한다. 커스텀 음성 학습은 후속 과제다.
		넷째, 표준 미디어 서비스와 차량 제어, 플랫폼 주행 제한 상태를 연동한다. 사용자가 방송을 시작한 후 음악 검색과 추가 화면 조작을 최소화하도록 설계한다.[S04][S08]
	5-4) 주요 사용 시나리오
		가족 여행: 플랫폼이 설정을 허용하는 상태에서 두 사용자가 각각 선호 시대를 고른다. 사용자가 재생을 누르면 첫 시대의 곡과 짧은 DJ 소개가 시작된다. 이후 공통된 분위기를 설명하는 브리지 멘트를 거쳐 다른 시대의 음악으로 전환한다. 대화를 강요하거나 음성을 수집하지 않으며, 사용자는 재생 제어만으로 방송을 이어 듣는다. 카세트 저장은 본 MVP 시나리오에 포함하지 않는다.
		비 오는 저녁: 사용자가 재생을 선택하면 앱은 유효한 강수 정보와 음악 취향을 반영한다. ‘퇴근길’은 사용자가 선택한 경우에만 사용한다. 날씨가 확인되지 않으면 시간대와 취향만으로 방송한다.
		통화·내비게이션 안내: 플랫폼 오디오 포커스에 따라 음악과 DJ를 감쇠·중단한다. 통화 종료 후에는 이전 사용자 재생 의도와 포커스 상태를 확인하여 재개한다. 종료되거나 취소된 멘트는 뒤늦게 재생하지 않는다.[S09]
		통신 장애: AI 응답이 실패하면 기본 멘트 또는 음악만 재생한다. 재생 가능한 로컬 콘텐츠가 있을 때만 오프라인 청취를 이어가며, 음원이 없으면 사용 가능한 상태를 정확히 안내한다.
	5-5) 개발 계획
		개발 담당 1인은 Kotlin 기반 차량 앱과 미디어 서비스, 상황별 편성, FastAPI 기반 LLM 중계, TTS 및 차량 기능 통합을 담당한다. 기획 담당 1인은 콘텐츠·DJ 대본 기준, 사용자 평가, 기획서 검수와 발표를 담당한다.
		Media3의 MediaLibraryService와 미디어 세션을 중심으로 콘텐츠 탐색 및 차량 재생 제어를 구현한다. Pleos TTS는 합성·중단·완료 및 오류 처리를 먼저 검증하고, 앱의 재생 조정자가 음악과 DJ의 상태를 관리한다. CarUxRestrictions에 따라 제한된 조작을 비활성화한다. Vehicle SDK는 기능 지원과 승인 권한을 확인한 항목만 사용한다.[S04][S05][S06][S08][S10]
		편성기는 허용된 음원 목록에서 곡을 선정하고, LLM은 해당 곡의 검증된 메타데이터에 한정하여 대본을 작성한다. 대본·편성 결과를 캐시하며, 음성 파일 캐싱은 공급자 지원과 이용 조건 확인 후 검토한다. 서버에는 인증, 요청량 제한과 공급자 장애 대응을 적용한다.
		첫 단계에서 음원 공급·미디어 서비스·TTS·주행 제한을 검증하고, 두 번째 단계에서 편성과 날씨·대본 생성을 연결한다. 이후 사용자 평가와 장애 테스트를 거쳐 시연 빌드를 고정한다. 차량 연동 실패를 발표 직전에 발견하지 않도록 검증 순서를 앞당긴다.
	5-6) 기대효과 및 발전 가능성
		초기 대상은 서로 다른 음악 시대를 선호하는 가족 동승자이며, 혼자 듣는 레트로 방송은 보조 이용 상황으로 둔다. 기대효과는 상대방의 음악 발견, 공동 청취 만족도, 적은 조작으로 이어지는 방송 경험이다. 효과가 이미 입증되었다고 주장하지 않는다.
		초기에는 서로 다른 세대의 5쌍을 대상으로 한 형성 평가를 제안한다. 동일한 음원과 순서에서 DJ 유무만 바꿔 듣는 비교를 수행하고, 상대방 음악 발견, 공동 청취 의향, 멘트 방해 정도를 평가한다. 평가 순서는 교차 배치하며 정차 환경에서 진행한다. 표본 규모와 목표는 검증 계획이지 실측 성과가 아니다.
		예상 MAU는 지원 차량 규모 및 실제 유입·재사용 데이터 확보 후 산정한다. 계정 없는 MVP는 익명 설치 단위의 월간 활성 규모와 4주차 재사용률을 측정한다. 사람 수와 차량 설치 수를 혼용하지 않는다. 수치 목표는 파일럿 결과를 기준으로 설정한다.
		사업화는 콘텐츠 이용허락과 원가 검증, 플랫폼 등록 조건 충족을 전제로 한다. 초기에는 제한된 검증용 배포를 우선하며, 이후 가족 카세트, DJ 선택, 콘텐츠 제휴를 단계적으로 검토한다. 공개 무료 서비스와 무제한 AI 사용을 초기 확정 사업 모델로 두지 않는다.

6) 검증 및 담당자별 완료 조건
	6-1) 개발 담당
		미디어 탐색·재생·일시정지·다음 곡 제어가 에뮬레이터에서 동작한다.
		DJ 중 일시정지·다음 곡·세션 종료를 수행해도 뒤늦은 멘트가 재생되지 않는다.
		통화·내비게이션·앱 전환·절전 복귀에서 재생 상태와 사용자 의도가 유지된다.
		주행 제한 활성화 또는 상태 미확인 시 상세 설정이 잠긴다.
		AI 오류, TTS 오류, 날씨 오류, 음악 파일 오류를 독립적으로 테스트한다.
		로컬 음원 경로에서 재생 요청 후 첫 오디오 출력 지연을 측정한다. 기존 3초는 검증 전 목표로만 남기며 온라인·오프라인·첫 실행을 분리해 기록한다.
	6-2) 기획 담당
		사용자 테스트 모집 및 질문지를 준비하고, 곡·DJ 대본의 사실과 표현을 검수한다.
		음원·효과음·이미지·목소리의 이용 범위와 증빙을 정리한다. 권리 판단이 필요한 부분은 권리자 또는 공급자 확인 대상으로 남긴다.
		시연에 쓰인 상황값이 실제 조회인지 모의 입력인지 구분하고 발표에 표시한다.
		한 줄 소개부터 발전 계획까지 MVP와 후속 기능 표기가 일치하는지 확인한다.
	6-3) 공동
		기획 검토 완료, 구현 완료, 사용자 검증 완료, 플랫폼 심사 완료를 서로 다른 상태로 관리한다.
		차량 안전 또는 세대 공감 효과를 보장하는 표현은 사용하지 않는다.
